Domain 1: コンテキスト障害の 4 大分類 (Failure Modes)

試験で最も頻出する診断シナリオです。障害の兆候から正確に分類できることが必須となります。

1. Context Poisoning (コンテキスト汚染) 高リスク

症状: 外部検索やツールから誤情報、ドラフト文書、古い規約がコンテキストに入り込み、エージェントがそれを真実と信じて推論を展開する。

対策: Unity Catalog で Authoritative (公式) 資産のみに検索を絞る、データソースの厳格な検証。

2. Context Distraction (注意散漫) 頻出

症状: 無関係な大量のログや無駄なテーブル行がプロンプトに溢れ、LLM のアテンションが埋没し、重要な指示や制約を見落とす。

対策: チャンクサイズの縮小、JIT 検索によるピンポイント取得、生ログのプルーニング。

3. Context Confusion (混同) 設計ミス

症状: 似た名前や類似した説明文を持つ複数のツールやカラムが存在し、モデルが誤ったツールや引数を呼び出してしまう。

対策: ツール説明文の差別化 (Disambiguation)、入力パラメータスキーマの厳密化。

4. Context Clash (衝突) 論理矛盾

症状: システムプロンプトの指示と、検索された文書内の指示や外部ツールの出力が矛盾し、エージェントがデッドロックや一貫性のない出力を出す。

対策: 指示の優先順位付け (システムプロンプト優先の明示)、競合するメタデータの排除。

Domain 2 & 3: Genie & Unity Catalog ナレッジ設計

Genie Space の Trusted Assets パターン

Genie に長文のプロンプトで集計計算式を書かせるのはアンチパターンです。 売上集計、MRR、顧客解約判定などの重要ロジックは、Unity Catalog 内で SQL UDF やビュー (Views) として事前定義し、Genie の「Trusted Assets」として登録 します。モデルは SQL 生成をハルシネーションすることなく、検証済みアセットを直接実行します。

Pre-inference vs Just-in-Time (JIT) 検索

項目 Pre-inference (事前取得) JIT Agentic (動的取得)
取得契機 モデル推論前に RAG で一括取得 推論中にツール呼出で動的取得
適した用途 単一質問、FAQ、ドキュメント要約 複数ステップ調査、最新テーブル参照
コンテキスト負荷 常に Top-K チャンクが占有 必要な差分のみ都度流入

Domain 5: MCP (Model Context Protocol) & Progressive Disclosure

段階的情報開示 (Progressive Disclosure) の 3 ステップ

80 個のツールの巨大な JSON スキーマをシステムプロンプトに常時展開すると、それだけで数万トークンを消費します。Progressive Disclosure ではコンテキストを 3 段階に分けて投入します：

Step 1: Discovery

ツール名と 1 行概要のリストのみを初期コンテキストに渡す (数千トークン削減)。

Step 2: Inspection

エージェントが必要と判断したツールのみ、動的に詳細な引数スキーマを取得する。

Step 3: Execution

引数を渡して実行。巨大な生出力は要約後に履歴からプルーニング (削除) する。

Domain 6 & 7: コンパクション鉄則 & マルチエージェント設計

Compaction の鉄則「Recall First」

長時間の対話で要約を行う際、最初から短さを追求すると「ユーザーの指定した除外ルール」や「エンティティID」が脱落します。 第1段階として必要な制約・変数を100%拾い切る (Recall 優先) チューニングを行い、その後に冗長な中間思考を削る (Precision 最適化) のが Databricks の推奨アプローチです。

Orchestrator のコンテキスト飽和防止

サブエージェントが 10 万行のデータを分析した際、親に生データをテキストで返すと親のコンテキストが即座にパンクします。 サブエージェントは詳細データを Unity Catalog の Delta テーブルに書き込み、親には「Delta テーブル URI」と「軽量な構造化サマリー (200トークン)」のみを返す のが本番アーキテクチャの急所です。
